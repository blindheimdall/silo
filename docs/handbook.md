# SILO handbook

A local workspace for AI agents, drawn as an underground silo. The whole screen is the world: 144 levels in 3D, round galleries, one spiral concrete stair in the middle, rooms in the outer wall and pixel-art residents walking the galleries. Terminals open on top of the world only when you ask for them.

## Start

You need Node.js 22 or newer and a browser with WebGL 2. Three.js is included in `public/vendor` with its license, so nothing has to be installed to run it. If WebGL is not available, a 2D version of the silo is used instead. Run `npm ci` only if you want the development dependencies.

```powershell
npm start
```

Open **http://127.0.0.1:3000**. `Start-Silo.cmd` does the same thing. Keep the window open while you use scheduled workflows, and stop it with Ctrl+C. The server only listens on this computer, not on the local network.

After updating the code, restart the server once. On the first start it updates `data/state.json` (see "Residents" below).

### Install, start at sign-in and updates

`Install-SILO.cmd` installs SILO for your Windows user, without administrator rights: the app goes to `%LOCALAPPDATA%\Programs\SILO`, your data to `%LOCALAPPDATA%\SILO\data` and the workspace to `Documents\SILO workspace`, so an update never touches them. It checks for Node.js 22 (and offers `winget install OpenJS.NodeJS.LTS`), adds SILO to the Start menu and to Settings, Apps, and asks whether SILO should start when you sign in. It can copy your residents and keys from this folder's `data`; that folder stays as it is. Options: `-InstallDir`, `-DataDir`, `-WorkDir`, `-Port`, `-FromData`, `-StartAtSignIn`, `-NoShortcuts`, `-NoRegistry`, `-NoLaunch`, `-Quiet`. Running it again updates the app and keeps the folders it used before. Uninstall from Settings, Apps; your data and workspace stay unless you type DELETE.

`npm run supervised` (and the installed shortcuts) start SILO under a small supervisor. It starts SILO again after a crash, waiting longer each time up to a minute, restarts it after an update, and writes `data/logs/silo.log` (5 MB, plus three older files). In System, Updates and start, you can turn start at sign-in on or off: it is a shortcut in your own Startup folder.

### Running without anyone signed in

- **Windows, with the computer.** In System, Updates and start, "Start with the computer, before sign-in" shows a command to run once in PowerShell opened as administrator: `powershell -ExecutionPolicy Bypass -File "<SILO folder>\installer\service.ps1" -Install -Start`. It registers a scheduled task that starts the supervisor 30 seconds after the computer starts, as you, without your password being stored (Windows calls it S4U), and starts it again up to three times a minute apart if it stops. It reaches the internet and your own files, not network shares, and it shows no windows, so desktop and browser residents need you signed in. One SILO runs per data folder: when you sign in and SILO starts there too, the second one sees the first and stops. `-Status` says whether the task is there, `-Install -DryRun` shows what would be registered, `-Uninstall` removes it. The uninstaller removes it too, as administrator, and stops with the command when it is not.
- **Docker.** `docker compose up -d` builds and starts SILO from the `Dockerfile`: Node.js 24, the app in `/app`, run as the unprivileged `node` user, your data in the `silo-data` volume and the workspace in `silo-workspace`. It comes back after a crash and with the machine (`restart: unless-stopped`), and the health check calls `/api/health`, which only says that SILO answers. The page is published on `127.0.0.1:3000` of the machine only. Set `TZ` so daily times are your local ones, and `SILO_SECRET` for a passphrase on the saved keys. In a container SILO does not update itself: build a new image (`docker compose build`, then `docker compose up -d`), and the volumes keep everything.
- **The first account from outside.** A SILO listening on every address (`SILO_HOST=0.0.0.0`, as in the container) answers any host name. Until the first account exists, only this computer, or a page opened once with the setup address SILO prints at start (`http://localhost:3000/?setup=<code>`), may use it; the code leaves the address bar at once and is kept in a cookie for a day. Make the owner account there. After that the code is no way in, and everyone signs in. A new code is made at each start. `SILO_HOST` takes an IP address only. To reach SILO from your network, make the accounts first, then publish the port beyond `127.0.0.1`.
- **Missed times.** A scheduled time that passes while SILO is off, asleep or paused is noticed when it is back, more than two minutes late. In the workflow editor, under the schedule, "A time missed while SILO was off" decides: run it once when SILO is back (the default), run it once only if it is at most 2 or 12 hours late, or skip it. However many times passed, it runs at most once, and Events says how many were missed, from when, and what was done. The API takes `catchUp` (`once` or `skip`) and `catchUpHours` (0 for however late, 1 to 168).

### Development, testing and production

Run one SILO for each environment, each with its own data folder (or container), and move workflows between them through a Git repository. In System, Environments and Git (owners only):

- **This SILO is** development, testing, production or none. The environment shows next to the connection state at the top, in red for production, so the two are not mistaken.
- **Repository and branch.** An https, ssh or git address, `user@host:path`, or the full path of a folder (a bare repository on a shared drive works). SILO runs Git as a program, never through a shell, without prompts, with hooks off and only over https, ssh, git or a folder. Git signs in on its own, with Git Credential Manager or an SSH key; an address with a password or token in it is refused. Git has to be installed (the container image has it). The working copy is in `data/sync/`.
- **Push workflows** writes every workflow to `workflows/<name>-<id>.json` and the layout of every table to `tables/<name>-<id>.json`, commits with what you wrote in "What changed" and you as the author, and pushes. Nothing changed, nothing committed. A workflow deleted here leaves the repository. If someone pushed in between, the push is refused: push again, and SILO starts from what is there. The API can push only some workflows (`ids`).
- **What goes, what stays.** A file holds the steps, the schedule and missed-time choice, the form, the shape, the budget, the tests and the judge, with residents named by name, role and sector, connectors and tables by name, and other workflows by their sync id. It never holds keys, passwords, the hook, form or app event addresses, table rows, runs, versions, or the mail and app triggers, which need an account of each SILO and stay as they are.
- **Look at a pull** fetches the branch and shows, without changing anything, each workflow as new, changed, the same, or one that cannot come (a connector or table missing, a step that does not pass the checks), the residents that stand in for others ("Ana is done by Bob here"), the tables that would be made or that have other columns here, and the workflows only this SILO has. A new workflow with the name of one made here is not ticked at first. Tick what to take and pull. If the branch moved since you looked, the pull is refused: look again.
- **What a pull does.** A workflow that came from Git before is changed in place: it keeps its id, whether it is on, its addresses, runs and lost events, and the version before is kept in its history. A new one arrives turned off, so you turn it on when the accounts it needs are there. A workflow that runs another one is pulled after it. Tables they use are made with their columns; a table here with other columns is left as it is. Nothing here is deleted.
- **Protect this SILO.** On production, tick it: then workflows are not made, changed, deleted, restored or given other tests here, and a held change is not applied. Turning a workflow on or off, its mail and app triggers and its local address are still allowed, and runs, approvals and evaluations go on. Change it in development, push, and pull.

Every push and pull is in Events and in the audit log, with the commit.

Updates come from a feed you set in System: an https address or a folder, also on the network. Nothing is checked until you set one. Every release is signed with an Ed25519 key, and SILO installs nothing until the signature, the zip and every file match. Releases never hold `data`, `workspace` or `launch.json`. The files an update replaces are kept, so Go back restores them, and an updated SILO that cannot start twice in a row is put back on its own. With "Install updates on their own", SILO downloads the update and installs it once no workflow, goal, conversation or request runs.

To make releases: `node tools/release.mjs --init-key` once (the private key goes to `%USERPROFILE%.silo
elease-key.pem`, keep it safe; `release-key.pub` goes into the app folder and out with every copy), then `node tools/release.mjs 0.2.0 --notes "What changed"`. Put `dist/silo-0.2.0.zip` and `dist/latest.json` in the feed.

## Moving around

- Drag left and right to turn around the shaft. Drag up and down, or scroll, to move between levels. Ctrl+scroll or the + and - buttons zoom. On touch screens, drag and pinch. The camera always eases into place, it never jumps.
- Keep zooming out and the camera leaves the silo: you see it cut open underground, with the earth around it, the crater and the airlock above it, the other silos on the plain and the ruined city far away. Scroll there to look at other depths, zoom in to go back inside.
- Click a resident to open their card. Double-click a resident to walk next to them, or double-click a floor to go to that level. Escape lets go of a resident or brings you back inside.
- The sector markers jump to a department. The slider on the right goes to any of the 144 levels, and the LEVEL box goes to an exact level. Up and Down move one level, Left and Right turn. The cutaway button switches between the view from far outside and the inside.
- The CRT button at the top turns the screen effect (scanlines, slight curve, glow) on or off. The choice is remembered.
- The lit signs on the walls (CONTROL, IT / UPLINK, RESIDENTS, SEQUENCES, OPERATIONS, ARCHIVE, and SECURITY on level 1) open their terminal.
- The bottom bar opens Residents, Flows, IT, Cameras, Signals, Archive and System. Alt + 1 to 8 opens them from the keyboard, and Escape goes back to the world.
- Locate, on a resident's card in the registry, moves the camera next to that resident.
- Ctrl+K searches everything: residents (by name, role, demo or live), levels (type 14 or L14 to go there), terminals, workflows, runs, Archive files and traces. Each result opens where it belongs.
- Keyboard: Ctrl+K search, Escape closes a window, Ctrl+Enter sends a message, Ctrl+S saves the open file. On the world: + and - zoom, 0 cutaway, Up and Down one level, PageUp and PageDown twelve levels, Home the top, End level 144.

## Terminals

- Every menu and window looks like the computers inside the silo: green phosphor text on black glass, amber for headings and the selected option, boxed DOS style headers, buttons that light up when selected, a blinking cursor and faint scanlines. Terminals open with a short CRT power-on flicker.
- The IT terminal starts with a status board: every provider line, whether it is online, its model, how many residents use it, and how many runs happened in the last 24 hours.

## Security room

- The Cameras terminal is a wall of monitors fed live from cameras placed around the silo: the surface sensor, the cafeteria, the stairwell from above, IT, the mids, engineering, the farm levels and the generator hall.
- Click a small monitor to put it on the big one. Drag on the big monitor to look around, scroll to zoom, or use the buttons and the arrow keys. Gallery and stairwell cameras can move up and down the levels (Page Up and Page Down).
- Click a resident on the big monitor, or pick one from the list next to it, to follow them. The camera turns with them and marks them with an amber box. From there you can talk to them, point a camera at them, or fly the world camera to them. Go there takes the world camera to the camera's level.
- The resident card and the registry have a camera button that opens the security room already following that resident.
- Follow the work (on by default): while a workflow runs, the big monitor turns on its own to the resident doing the current step and moves on when the next step starts. Turn it off from the card next to the monitors.
- The surface sensor gets dusty over the hours. Clean the lens to get a clear picture again. The big screen in the cafeteria on level 1 shows the same picture inside the 3D silo.
- Only one camera is drawn per frame, at a low resolution, and its picture is read back from the graphics card without waiting for it, so the world stays smooth while the monitors run.
- While a terminal is open the world behind it is redrawn about 20 times a second instead of every frame, and nothing blurs the live picture, which keeps the fans quiet.
- A camera picture keeps what it changes in the scene (lights, levels, residents, couriers) in buffers it reuses, so a running camera makes no garbage however many residents there are.
- To measure frame times on your machine, open SILO with `?debug` at the end of the address and run `await siloProfile()` in the browser console. It measures three scenes for five seconds each (`siloProfile({ms:10000})` for longer): the whole silo from afar, a close look at the level with the most residents, and the security room with all nine cameras running. For each it gives the frames per second, the late frames, the typical and slow frame times (p50, p95, p99 and the slowest) for the simulation, the drawing and the cameras, and the five slowest frames with what took the time. It shows three numbers apart: the target rhythm (the screen's, or about 20 frames a second on purpose for the security room and behind a terminal), the CPU time of the code, and the GPU time the graphics card itself took, measured with timer queries where the browser allows them (Chrome and Edge on most cards) and shown as not measurable elsewhere. It then says what holds the frames back: the code, the graphics card or nothing. Without a GPU time, the card's share is the time between frames beyond both the code and the target, so a pause the limiter makes on purpose is never blamed on the card. `node tools/profile-3d.mjs` runs the same in the browser of this computer and prints a row per scene.
- Without opening anything by hand, `npm run profile:3d` starts a SILO of its own with temporary data, opens it in Edge or Chrome in a hidden window and prints the same numbers with the name of the graphics card used. `npm run profile:3d -- --software` draws on the processor (SwiftShader), a stand-in for a weak card; `--show` uses a visible window, `--ms 10000` measures longer.
- On a card that cannot keep up (under 25 frames a second while the simulation takes a small part of each frame), the silo draws with less detail and lowers its sharpness step by step, down to 0.6 of the screen's, within a few seconds; it goes back up when the frames are on time again. Frames of several hundred ms count too, and a driver that makes the drawing call itself wait counts as the card. Measured with SwiftShader at 1424 by 805: a level up close went from about 490 ms a frame to about 170 ms, the whole silo from about 900 ms to about 740 ms. On a Radeon RX 9070 XT every scene takes 2 to 4 ms of work a frame and nothing is lowered.

## Residents

- There are 432 residents: at least three on every level, spread over six sectors (upper levels, IT, the mids, engineering, supply and farms, mechanical).
- Each resident has a name, a role, instructions, a uniform color, a level and a model. All of it can be edited, and residents can be added or removed.
- Every resident has a fixed look based on their id: skin, hair, build and gear that matches their sector (hard hats in engineering, headsets in IT, goggles and a wrench in mechanical and so on).
- When an older `state.json` is loaded, the server adds residents until every level has three. Residents that still have an auto-generated name like "Nora 002" and instructions you never edited get a real name and a role. Anything you changed yourself is left alone.

## What it does

- Saved conversations. Demo residents answer with a short scripted text marked `[DEMO]` and do not call any model.
- Model providers: OpenAI Responses, Anthropic Messages, local Ollama, and any HTTPS endpoint in the OpenAI chat completions format.
- Workflows: steps run in order. There are seven kinds of step:
  - **Resident**: one resident does the work. By default they get the brief and the output of the step before. Instructions can also place exactly what they need: `{{brief}}`, `{{previous}}`, `{{step 2}}` (the latest output of step 2), `{{step 2.name}}` or `{{previous.items[0].id}}` (one value out of an answer that is JSON), `{{feedback}}` (the last reviewer notes) and `{{file notes.md}}` (a workspace file up to 30 KB). The chips under each step insert them.
  - **Review**: a resident checks the work and answers APPROVED or REVISE. REVISE sends the work back to the step you chose, with the reviewer's notes, at most the number of rounds you set (1 to 5). After the last round the workflow goes on and the trace says it was not approved. Every step after the one it sends work back to runs again, so a review cannot send work back past an app step that changes something, like sending a mail: put the review before that step.
  - **App step**: SILO calls one operation of an app directly, with no model and no tokens. Pick a connector from IT / Uplink or an account (Google, Microsoft 365, Slack, GitHub, Notion; one that is not connected yet is marked, and the run asks you to connect it), then what it should do (reads and changes are listed apart), and fill its fields. A field can be plain text or take a value from before: `{{brief}}`, `{{previous}}`, `{{step 2}}`, or one value out of a JSON answer, like `{{step 1.id}}` or `{{previous.items[0].email}}`. Values are turned into the type the app wants (number, yes or no, list, JSON), and a request body is shown field by field. A missing value, a wrong type or an app that refuses stops the run and says which step and which field. A field that holds a saved key or password, also one kept in a connector's headers, is never sent, not even in a read. A field can only take values from the steps above it. A value that goes into an address, like an id or a file path, cannot be `.` or `..`, so it can never move the call to another address of the app. Test runs do not call operations that change something; they show what would have been sent. To confirm before a change, put an Approval step before it.
    - A busy app is tried again, up to twice by default (0 to 5, set per step), waiting 1, 2, 4 seconds and more in between. Reads are tried again after a timeout, a 429 or a 5xx answer. A change is only tried again when it surely did not happen: the app answered 429 or 503, or no connection was made. The trace says how often it was tried.
    - Connected accounts give app steps their answers as fields: the emails of a Gmail or Outlook search (id, date, from, subject, snippet), calendar events, files, sheet rows (one object per row, named by the first row; a second column with the same name becomes "name 2"), Slack channels and messages, GitHub repositories, issues and pull requests, Notion pages, and the id or link of what was made. Residents still get the same answers as text. A very long JSON answer, from an account or a connector, loses items from the end of its list instead of being cut in the middle, so later steps can still read it. A new sheet row never runs a formula: a cell that starts like one, like a mail subject `=IMPORTDATA(...)`, is written as text, while numbers and dates stay numbers and dates.
    - **Tables** are listed as apps too: find rows, one row by its id, count rows, add a row, change a row, change the row with a value or add it, delete a row. Each column is a field. In a find or a count, a filled field is a value the rows must have (text without case, a date as the whole day); order by a column, with `-` before it for the largest first, and a limit (50 when empty, 500 at most). A find gives the list of rows, so the next step can repeat over it. "Change the row with a value, or add it" finds the row by the column you name (like email) and says with `_added` whether the row is new, so a run that comes again never adds the same person twice. Operators add and change table steps too, since they change only SILO's own tables.
  - **Wait**: the run waits a number of minutes, hours or days (up to 30), or until a time of day, any day or one weekday. A waiting run keeps waiting through a restart of SILO and goes on by itself, and Stop cancels it. While it waits, the workflow does not start again. A waiting run holds no place in the job queue and does not hold back an update: it keeps waiting through the restart. Test runs do not wait.
  - **Code**: a few lines of JavaScript turn earlier answers into the next one, with no model and no tokens. The code gets `input` (the brief), `previous`, `steps[1]`, `steps[2]`... (earlier answers as text), `item` in a step that repeats for each item, and `json(text)`, which reads JSON out of an answer, also when there is text around it. What it returns is the answer: text as it is, anything else as JSON. It runs at once (no `await`), for at most 5 seconds and 64 MB, in a worker with a fresh context that holds only a copy of that data: no `require`, no `process`, no network, no files and no `eval`. Only an owner adds or changes a code step, because it runs on the server. It keeps mistakes small; it is not a sandbox for code from people you do not trust.
  - **Run a workflow**: another workflow runs as one step and the run waits for it, approvals and waits included. Its brief is the step's text, with `{{brief}}`, `{{previous}}` and the rest, or the answer before when the text is empty; its final answer is the step's answer. Its run shows in the history with the name of the run it belongs to. Stopping the outer run stops it; a failure, a stop or a check inside fails the step with that reason. A resume or a retry finds the same inner run again, so it never starts twice for one step: a finished one gives its answer, a stopped one goes on. Workflows that run each other in a circle, or a workflow running itself, are refused when saved, and runs go at most 3 deep.
  - **Approval**: the workflow stops and waits for you. Approve it with an optional note, which the next resident gets, or reject it to stop the run. A toast tells you when a workflow is waiting.
- **For each item**: an app step, a code step or a resident step can repeat once for each item of a list from before, like `{{step 1}}` or `{{previous.items}}`, at most 100 items, one after the other. An answer like `{"data": [...]}` with one list in it works too, and so does a brief or a resident's answer written as lines, with or without list marks: one item per line. Inside the step, `{{item}}` is the item and `{{item.email}}` one value of it. The step's answer is the list of its answers, so the next step can repeat over that. A resident gets only its item, not the whole list. An empty list does nothing; a list that is too long, or an answer that is not a list, stops the run before anything is sent; an item that fails stops the run and names the item. All the answers together stay under 300,000 characters: with many items, each answer is kept shorter, and JSON stays JSON. Each item done is saved with the run, so a run resumed after a stop, a failure or a restart goes on with the next item and never does one twice. In a list field, the commas you type split the items, so a value with a comma in it, like a date, stays one item.
- **Answers from apps are data**: when a resident gets the whole answer of an app step, an item from one, or one value of it that is long or has several lines, like the text of an email, it comes marked as coming from outside SILO, with the rule not to follow instructions inside it. The mark cannot be closed from inside the answer.
- **Same time**: a resident step can run at the same time as the resident step above it. Steps that run together get the same input, and the next step gets all their answers, each marked with its step and resident. A resident who is in two of them does them one after the other.
- **Conditions**: any step can be set to run only when (or unless) the previous answer, or the answer of a chosen earlier step, contains a word or phrase. Skipped steps show in the trace. Two steps with opposite conditions make a branch.
- **Triggers**, all only while the server is running:
  - every N minutes, or every chosen weekday at a fixed time;
  - a local webhook: `POST http://127.0.0.1:3000/hook/<address>` with the brief as plain text or as JSON `{"input": "..."}`. The answer holds a `check` address that returns the run's status and final output. Only programs on this computer can reach it. The address is secret, and you can replace it in the editor;
  - a watched workspace folder: each new or changed text file starts a run with the file in the brief. Files already in the folder when you turn it on are left alone;
  - an email: SILO checks an IMAP inbox every minute and starts a run for each new message, with the sender, subject and text in the brief. You can keep only mail from a sender or with a word in the subject. Mail that was already there is left alone, and messages stay unread. The connection uses TLS on port 993. Gmail and Outlook need an app password. The password is kept in the vault for that server and account only: changing the server, port or user asks for it again, and a connection test uses the saved one only for the saved server.
  - your phone: `/run` in the Telegram bot (see Phone below).
  - a public form: tick A public form people fill in, give it a title, a line under it and up to 12 fields (short or long text, email, number, date; each needed or not), and save. The form gets an address, `/form/<address>`, that anyone with it can open, also from the internet when remote access is on. Each answer starts a run with the fields as JSON, so an app step can use `{{brief.email}}` and a code step `json(input).email`. Emails, numbers and dates are checked, and a wrong answer comes back with what was typed. A hidden field catches simple bots, and one address may send 5 answers a minute, a form 60. New address on save retires the old one, and viewers do not see it. While a run of the workflow goes on, answers wait in its queue.
  - another workflow that failed: When a run fails, start picks a workflow that gets the failed workflow, the run, the step, the error and the brief as JSON, after the last retry. A run started that way does not start another one when it fails too, so two workflows that watch each other stop after one round. Test runs never start one.
  - something new in an app: a new email in Gmail or Outlook, a new row in a Google Sheet, a new or changed file in Google Drive, a calendar event about to start, a new message in a Slack channel, a new issue or pull request on GitHub, a new or changed page in a Notion database. Without any account: a new item in an RSS or Atom feed, or a web page that changes (optionally only when it contains a word you pick). SILO asks the app every 15 seconds, every minute or every 5 minutes (you pick; feeds and web pages at most once a minute) with the account connected in IT / Uplink, starts one run for each new thing, and puts it in the brief marked as coming from outside. What was there before you turned the trigger on is left alone. A check that fails shows why on the workflow and is tried again a few minutes later.
    - Instant events. GitHub issues and pull requests and Slack messages can also arrive the moment they happen. Tick Instant, save, and open the workflow again for the address to give the app. GitHub signs each event with a secret SILO makes, and SILO can add the webhook to the repository for you with your token (it needs the admin:repo_hook scope or Webhooks write). Slack needs an app of your own: paste its signing secret, and give the address under Event Subscriptions. Events with a wrong signature, or Slack events older than 5 minutes, are refused. The regular checks keep running, and one issue or message never starts the workflow twice. The address has to be reachable from the internet, so this needs remote access turned on.
    - Events from about 40 more apps. Pick "An app sends an event" and the app: Stripe, Shopify, WooCommerce, Square, Paddle, Lemon Squeezy, GitHub (any event), GitLab, Bitbucket, Sentry, PagerDuty, Vercel, Netlify, Jira, Linear, Asana, Trello, ClickUp, Todoist, Notion, Calendly, Typeform, Zoom, Discord, a Telegram bot, WhatsApp, Facebook and Instagram, Twilio, Mailgun, Resend, Clerk and other apps that sign with Svix, Zendesk, Intercom, HubSpot, Webflow, Dropbox, Postmark and Pipedrive (user and password), and any other app that signs with HMAC SHA-256 or sends a secret in a header. Give the secret the app shows (the editor says where to find it), save, and give the app the address. SILO checks each event the way that app signs it, refuses a wrong signature and, where the app sends the time, anything older than 5 minutes, and answers the app's own address checks (Asana, Notion, Dropbox, Meta, Trello, Zoom, Discord). Asana and Notion send their secret when the webhook is made, so there is nothing to type. You can keep only some events, like "invoice, checkout.session". Each event starts the workflow once.
- **Describe it**: say in your own words what should happen, and a resident with a model drafts the workflow: its steps, the residents, apps and tables it uses, when it starts and a public form if it needs one. The resident sees your residents (name, role, tools), the apps with their operations and fields, your tables with their columns and your workflows, and nothing else of SILO. Its draft is checked with the same rules as a saved workflow; a draft that does not pass goes back with the reason, three tries at most, and when none passes you get the last reason. The draft opens in the editor with a note on what to set up first; nothing is saved or started until you save it. "Change the last draft" asks for a change instead of starting over. For a person who is not an owner, the draft uses no code steps and no app steps other than tables. Closing the window stops the resident, and a draft takes 3 minutes at most. It counts in spending like any other answer.
- **Versions**: every saved change to a workflow keeps the version before it, up to 20. Versions shows them side by side, and Restore brings one back as a new version. Each run records the version it ran.
- **Replay**: a finished run can be replayed with the same brief, from the start or from a chosen step. From a later step, the earlier steps keep the answers of the old run and are marked as such in the trace.
- **Tests**: a workflow and a resident can each keep up to 20 test cases. Open Tests on a workflow, or the check button on a resident's card. A case is a brief (for a resident, a message answered as a new conversation, its chat history neither used nor changed) plus checks on the answer, one per line:
  - `contains:`, `missing:` and `regex:` look at the text;
  - `field: total=1200` compares a field of the result shape (workflows only);
  - `judge: names the supplier and the due date` has a resident score the answer from 0 to 10 against the requirement; it passes at 7;
  - `maxcost: 0.05` (dollars), `maxms: 30` (seconds) and `maxtokens: 5000` are limits for one attempt;
  - `x2` to `x5` after the kind, like `judge x3: ...`, makes a check count more in the score.

  A case can also keep a **reference answer** you approve; the judge gets it to know what a good answer holds. Approval steps pass on their own, and nothing in a test run changes anything: app steps that change something are not called, and residents use only the tools that read (files, the archive, web pages and search). A tool that would write, send, run code or reach outside SILO is not run, whatever its policy or an approval says, and the resident is told what it would have sent. This also holds for a resident asked by another one during the test. Test runs and their traces never push out real ones, and they do not sound the alarm.
- **Several runs per case**: each case runs 1 to 5 times (3 by default). A case passes when every run passed and is **flaky** when only some did. Each report has a score from 0 to 100 (the mean of the case scores, weights and judge scores included) and the pass rate over every run with its 95% interval.
- **Case by case against the report before**: every case is marked broke, fixed, worse, better, flaky, new or the same compared with the last report on the same model. A case breaks when it passes clearly less often than before (by half or more), not after one unlucky run. A report **got worse** when a case broke, a case scored clearly lower while passing as often, or the pass rate over every run fell more than chance explains (a one-sided test at 95%). Then there is an event and a notification. **Compare** shows a case's answer next to the one before it, and what changed in between: the steps, the prompts and models of the residents in them.
- **Tests on a change**: in Tests, choose what happens when a resident's prompt, model or tools, or a workflow's brief or steps change:
  - *Nothing happens*;
  - *Run the tests* after the change. A resident's change also runs the tests of every workflow with that resident whose tests run on change.
  - *Hold the change until nothing got worse*. The tested part of the change waits as a **held change**, not in use; the rest (a name, a schedule) goes in at once. Its tests run, after a run of the current version when it has none. When nothing got worse the change goes in by itself. Otherwise it waits for you: What changed shows the difference, and you apply it anyway, reject it or test it again.

  A resident whose tests got worse, or whose change made a workflow worse, shows an orange down arrow in the silo and "Tests got worse" on its card until a later report is fine again.
- **Cases from real work**: a finished run of a workflow, or the last answer of a resident, becomes a case in one click, its answer the reference. With **Learn from rejections** on, a run you reject with a note becomes a judged case on the same brief.
- **A judge you can check**: mark each judged verdict Right or Wrong. Below 80% agreement over 5 or more verdicts the judge is marked unreliable and SILO does not pick it on its own. Without a chosen judge, SILO picks a resident with another model than the one doing the work when there is one, and the report says when the judge shares the model.
- **Compare models**: in Tests, pick up to three models. The same tests run once per model, every step on that model, and a table shows passes, score, cost, time and tokens side by side.
- **From CI**: `SILO_TOKEN=silo_pat_... npm run eval` runs the tests of every workflow and resident that has them (or only those named: `npm run eval -- "Invoice reader" Atlas`), waits, prints each report and exits with 1 when one got worse or did not finish. Options: `--url`, `--repeat 1-5`, `--min-score 0-100`, `--strict` (every case must pass), `--timeout` seconds, `--json`. The token needs the read and run scopes. SILO keeps the last 40 reports per workflow or resident; the answers of cases stay in the newest 8.
- **Result shape**: a workflow can promise fixed fields (text, number, date, yes or no, list), as one object or a list of them. The last resident step is told the fields, and SILO checks the answer at the end of every run: missing fields, numbers that are not numbers, dates that are not dates. "1,200.50" becomes 1200.5 and "no" becomes false. A wrong answer goes back to that resident once for a fix; if it is still wrong, the run fails and says what is wrong. The run output is the clean JSON, and the webhook `check` address returns the fields as `data`.
- **Token budget**: a run stops before its next step once it has used the set number of tokens. Raise the budget and resume the run to finish it.
- **The Order**: the book of procedures of the silo, opened from Flows. Twenty-two procedures in six chapters:
  - Knowledge: Research brief, Decision memo, Council session;
  - Making: Code change with review, Article;
  - Standing orders: Inbox triage, Morning report;
  - Office work: Invoice to fields, Meeting notes to tasks, Mail digest (Gmail or Outlook), GitHub issue triage, Weekly report in Word;
  - Apps on their own: Mail into a sheet, Issues into Notion (both with no model), Today in Slack (calendar, a resident writes the agenda, your OK, then Slack), Ask, wait, sum up (a Slack question, two days of waiting, a summary in the channel). Fields like the sheet link or the Slack channel say "Paste ... here" until you fill them in;
  - Tables: Contact form into a table (a public form keeps each message in Leads, a resident drafts a reply, and after your OK the reply is kept with the lead), Sorted feedback (a form, a resident gives the topic and the mood, a few lines of code keep anything it did not say right as other and neutral, then a row in Feedback), Event signups (a form; the same email changes its signup instead of adding one, and each run says how many signed up; no model), Low stock (every weekday, code finds the rows of Stock at or under their minimum, and only then a resident writes the order list), Leads of the week (every Monday, the leads of the last seven days summed up and posted to Slack after your OK), Failure log (choose it under "When a run fails, start" in your other workflows, and every failed run is kept in Failures with the workflow, the step and the error; no model).

  Find a procedure by words in its name or description, or show only the ones ready to run: a lit dot means its accounts are connected, its tables are there or will be made, and a resident has a model. Each page starts with what it needs, marked READY, NEW (a table made when you adopt it) or TO DO (with where to set it up). Adopting a procedure with tables shows the tables and their columns first and makes the missing ones in the Archive; a table with that name that is already there is used as it is. A procedure from a file whose table is missing says to make it in the Archive first. App steps that only use tables can be adopted by operators too; other app steps still need an owner.

  Each page names the residents who would carry out every step, the permissions a step needs and whether that resident has them, the conditions, reviews and approvals, the result shape, and how it starts. Adopt a procedure to open it in the editor, where you can change anything before you save. Test cases that come with it are saved with the workflow.
- **Share and import**: Share on a workflow gives it as a procedure file (`.silo.json`) or keeps it in the Order under Your procedures, for everyone on this SILO.
  - The file holds the steps, their instructions, the name, role and sector of each resident, the result shape, and the tests with their briefs. App steps keep what they fill in, like addresses, channels or sheet links, so read them before you send the file; a connector goes by its name, and the SILO that imports it uses its own connector with that name. It holds no keys, webhook addresses, mail settings, runs or files.
  - Import a procedure, in the Order, reads a file or pasted text and checks it with the same rules as a workflow. Anything else in the file is dropped.
  - You read it as a page of the Order before anything is saved. Residents are matched by name, then by role, then by sector.
  - A procedure from a file never starts on its own and gives no resident a new permission. Its instructions become instructions for your residents, so read them first.
- **Couriers**: every time a step hands work to a resident, a courier carries the folder through the 3D silo: along the gallery, over the bridge, up or down the spiral stair and over to the next resident. The first step comes down from level 1. A faint amber outline keeps the courier visible behind the stair core. Watch the courier, in the run trace, rides the world camera along with it and on to the next courier.
- Each workflow step starts from a clean conversation. It does not see the resident's chat history and is not added to it.
- The trace shows the text of the current step as it is written. Every run is saved with each step's output, tokens, reviews and errors.
- Rate limits, overloaded providers and dropped connections are tried again up to three times. An answer that hits the model's output limit is continued up to two times, and the trace warns if it was still cut off.
- A run that reaches a step while SILO is paused is interrupted, not failed: it is not tried again or undone, and it is resumed by hand, or by crash recovery for a job. A run whose token budget is used up fails without retries or undo; raise the budget and resume it. Jobs cut off by a stop go on from their last checkpoint when SILO starts again, unless the queue settings turn recovery off.
- A failed, stopped or interrupted run can be resumed from the step where it ended. If the save of the resume fails, the run goes back to how it was (status, error, budget and log line) and the resume answers 503; a queued job whose start cannot be saved stays queued with its run and starts at the next try, as a manual start does. The steps that already finished are kept. Resuming takes the residents as they are now, so a resident you fixed is used, and the activity log names the ones that changed. Retries of a job and recovery after a crash keep the instructions and model the run started with; a permission taken away since then is gone at once, one added since then is not used.
- What a run has already done is not done again. Each tool call and each app step that changes something is saved the moment it succeeds; after a crash, a retry or a resume, the same call gets the saved answer instead of being sent twice. A resident asked for help with ask_resident writes into the same journal, under a place of its own for each call (the step, the round, the call and the helper), so what the helper changed outside SILO is listed by a rewind and not sent again by a resume either. In a step that repeats for each item, each item has its own place too: two items that give a tool the same arguments are two calls, not one call and a saved answer. When a Shadow steps in and leaves a change unsure, the run waits for your check with what was sent, as it would for the first resident.
- A run keeps one journal of these results, each saved once and numbered. A checkpoint only notes how far the journal had come, so a long run does not carry a copy of every earlier result in each checkpoint. Rewinding a job to a checkpoint drops the results that came after it. A job keeps its journal after it finishes, so it can still be rewound safely.
- A rewind never repeats a change outside SILO by itself. When going back to a checkpoint would make an order, an email or another change again, the rewind stops and lists each one (app, operation, step, what was sent and whether it went through). Rewind again with `repeat: false` to keep what was done, so the steps after the checkpoint get the saved answer, or with `repeat: true` to do it again. The activity log says which you chose.
- A change outside SILO whose result is unknown waits for you. An app step or a resident's tool that changes something in an app or connector (sending an email, writing to a sheet, an MCP tool that is not read-only) is written down before it is sent. If the connection breaks after sending, the answer does not come in time, a gateway in front of the app gives up (502, 504, 408) or SILO stops in the middle, the run is not retried and not failed: it shows **Check needed** with exactly what was sent. Look in the app, then press **It went through** (optionally with what the app shows, such as an order number, for the next steps) or **It did not, send it again**. Nothing is sent again until you answer, also after a restart or a resume. A service can make a change and then fail before it answers, so any 5xx answer (500 and 503 too) leaves the result unknown in the same way. Only an answer that refuses the change (400 to 429, except 408), a refused connection, an unknown address or a missing sign-in prove that nothing was done. A change is tried again by itself only after 425 or 429, or when nothing was sent; a 503 is never tried again by itself.
- A run exists only once it is saved. If the save fails, the run is taken back out with its own log lines (by their id, so a line another run wrote meanwhile stays), the start answers 503, and a queued event stays in the queue, so a run that never started cannot hold back the workflow. A scheduled run is saved together with its next time, and a lost event started by hand leaves the list in the same save as its run, so neither can start twice.
- App triggers never lose an event between two checks. Gmail, Outlook and Google Drive are read page after page until what was seen before, and at most 10 mails or 20 files are handed on a check, the oldest first; the rest come at the next check. The mark of what was seen moves only past what was handed on (for Drive, files changed in the same second as the last one handed on are remembered, so none is skipped or given twice).
- What a check hands on is saved in the workflow's inbox in the same save as the new mark, before anything starts, and each event leaves the inbox in the save that holds its run or queue entry. If SILO stops in the middle of a batch, the rest start after the restart, and none starts twice. Instant events are saved the same way before SILO answers the app. At most 100 wait in the inbox; older ones are counted as dropped and the log says so.
- Slack, Notion, GitHub and the Outlook Calendar are read page after page too. Slack reads everything after the mark (up to 5 pages of 200), hands on at most 20 messages a check, the oldest first, and moves the mark only to the last message it looked at. Notion reads edits in time order (up to 5 pages of 100), at most 20 a check, and remembers the pages already handed on in the same minute, since Notion keeps edit times to the minute. GitHub reads newest first until a number it has seen and hands on at most 20 issues or pull requests a check, the oldest first. The Outlook Calendar follows every page of the window (up to 5 of 50).
- A Google Sheet trigger without an id column sees a new row by its number and content: a row added at the end starts the workflow, and a row deleted and replaced by another with the same number counts as new. It assumes rows are only added at the end (append only): a row inserted in the middle, or rows moved, shift the numbers. For sheets edited anywhere, give the header of a column with a unique id (an order number, an email, any value that never repeats). Each row is then known by that value wherever it is; a row whose id is still empty waits until it is filled, and a missing column stops the check with a clear message. The ids of rows deleted from the sheet are forgotten, so the list of ids never pushes out a row still there. Without an id column a sheet is read up to row 5000.
- Gmail and Outlook hand on only mail that came after the newest message seen before: old mail met for the first time (on a later page, or moved back into the inbox) is not new. Notion's first mark is the start of the minute the trigger was turned on, since Notion keeps edit times to the minute. A web page that changes back to how it was before counts as a new change each time.
- While a workflow runs, is paused or has no power, the events an app hands on wait in its inbox (up to 100) instead of its queue of 15, and start one after another once it is free; a workflow set to skip while busy still skips them. A check of an email inbox saves its new mark, the first mail's run and the queue of the others in one save. A file is marked as seen once it starts a run, joins the queue or is skipped, so the same version is never taken again; a start that fails puts it in the queue.
- GitHub issues found by a check are new by number: an issue that gets the chosen label after a newer labelled issue was handed on is not started by the check (an instant event for the label is). Slack thread replies come only as instant events, since a check reads the channel itself.
- Queued triggers leave the queue only together with the run they start. One that cannot start stays queued and is tried again, up to five times.
- A workflow card shows the events waiting for it, since when, and why: SILO is paused, a run of it is still going, its sector has no power, or its last start failed. It also counts what never ran: events dropped because 15 were already waiting (the oldest goes, and the log says so), events given up after five failed starts, and events skipped because the workflow skips while busy. Dropped and given up events (also app events pushed out of a full inbox) are kept apart with what they carried, when they came and why, the last 30 a workflow. Under Lost events on the card each can be started again by hand or let go. Skipped and merged events are only counted: they follow the workflow's own setting, and merging stays for flows where only the latest state matters.
- Old runs and jobs are dropped only once they are finished, the oldest first. One that runs, waits or can still be tried again is kept however old it is.
- A running workflow can be stopped at once from its trace, even in the middle of a step. Finished runs can be started again with the same brief, and every output can be copied.
- If a step's resident is busy with another mission, the step waits for them instead of failing.
- A workflow can keep a saved brief. Scheduled runs use it, and it is filled in when you run the workflow by hand.
- Workflows can run on a timer while the server is on. A workflow never runs twice at the same time. A trigger that arrives while the workflow is already running, its first resident's floor is on low power, or its run fails waits in a queue of up to 15 and runs once the workflow is free. The workflow's `missedPolicy`, set through the API, decides what is kept: `coalesce` (the default) keeps one copy of a repeated trigger, `queue` keeps every one, `skip` drops them. Pause stops new missions and stops a workflow between steps. Requests already sent still finish.
- Conversations sent to a model leave out failed exchanges and always start with your message, so long chats keep working with every provider.
- Shared text files in `workspace/`.

  - **Propose files**: a file the resident writes waits in the Archive under "Waiting for your approval". View it (next to the current file if it replaces one), edit it before saving, save it or discard it. The Archive key shows how many are waiting.

  - At most 12 tool uses per answer. Every use shows as a line in the chat and in the workflow trace, and failed ones are marked.
  - Tools use each provider's own tool calling. Models without it, such as some local models, fall back to a short text block the resident writes, so tools still work. A weak model may not use them well.
- **Traces**: every conversation, workflow run and goal is recorded as a trace: each step, model call, tool use, question to another resident and wait for your approval, with its time, tokens and cost (at the prices you entered), what it was given (secrets hidden), what came back, and the files it proposed. Signals lists the last traces, a workflow run has a Time and cost button, and every answer in a conversation has a TRACE link. The view shows a waterfall, so you see what ran at the same time and where the time went. A running trace updates itself. The last 40 traces are kept.
- **Spending**: enter the price per million tokens for a model (or for every model of a provider) in IT, and SILO counts the money per day and month. A daily, monthly or token limit per provider warns at 80 percent and is never passed: each call is checked before it is made, the first one too, for the whole question and the longest answer it may get. When less is left, the answer is asked to be shorter; when there is no room for a short answer, the limit counts as reached and new calls to that provider are blocked until the next day or month, or until you raise it. A model without a price has an unknown cost: its calls are counted as such (Spending shows "+ unknown", never $0), and while its provider has a daily or monthly money limit they are refused with a request to set the price. Spending lists those models above the table, since the money limit does not cover them until they have a price.
- **Notifications**: Telegram, Slack, Discord, email over SMTP, or a webhook of your own (signed with HMAC SHA-256 when you give a secret). Each channel picks what it hears about: failed or finished workflows, approval requests, proposed files, spending limits, test results.
- **Phone**: a Telegram bot of your own, set up in IT. Create it with @BotFather, paste the token, press Pair a phone and send the code to the bot. Only paired private chats are obeyed, at most five. From the phone you can:
  - talk to a resident (`/talk name`, then just write); the answer is the same conversation you see in SILO;
  - list and start workflows (`/flows`, `/run 2 your brief`), and get the result back when the run ends;
  - allow or deny a resident's request, and approve or reject a waiting workflow, with buttons under the message;
  - see what runs and what waits (`/status`, `/pending`), and pause or resume the silo.
  SILO asks Telegram for new messages (long polling), so it works without a public address or open ports. The bot only works while the server runs.
- **Voice**: the Talk button in a chat writes what you say into the message, so you can check it before sending, and READ on an answer reads it aloud. You can also have every new answer read aloud. Set it up in System, Voice:
  - Speech to text runs in SILO through OpenAI (`gpt-4o-mini-transcribe` unless you name another model) or a compatible endpoint, or in the browser. Edge sends the sound to Microsoft for this and Chrome to Google. By default SILO uses OpenAI when it has a key, and the browser otherwise.
  - Answers are read by the voices of your device, free and on the device, or by OpenAI or a compatible endpoint. Paid calls count in Spending and stop at your limits.
  - The microphone works on this computer and over HTTPS (Open from anywhere), not over plain HTTP on the network.
  - Voice notes sent to the phone bot are turned into text when speech to text runs in SILO. The bot answers with what it heard. What was said always goes to the resident as a message, never as a command.
- **Windows notifications**: turned on in System, for the events you pick. For an approval request the notification has buttons. A button opens a one-time page in your browser, and the decision is made only when you press the button on that page. Links work once and for 30 minutes.
- Buttons that open Notepad, Calculator and the workspace folder.
- Activity log, search, and a JSON export without API keys.

## AI on this computer

Chrome and Edge 138 and newer carry small AI models of their own. SILO uses them for three things, inside the browser, without a key, without cost, and without sending the text anywhere:

- **Translate** on every answer in a chat and on every step of a run. The language is found by itself, long answers are translated piece by piece so the first lines show at once, and languages without a direct pair go through English. Code is never translated: blocks between ``` fences stay exactly as they are, and inline code keeps its place in the translated sentence.
- **Key points** on answers longer than a few paragraphs. Text longer than the model takes is summed up in parts, then the parts together. The summary model writes English, Spanish and Japanese; for other languages its key points are translated.
- **Brief me** in Signals sums up what happened in the silo over the last day. Without the summary model it counts what happened and lists the errors and the latest events instead.

Pick the language in System, AI on this computer. There you can also have new answers in another language translated by themselves (only answers to what you send from that chat, not older ones), and download the models with one click. The language packs are small and come down on first use; the summary model is a few gigabytes, needs a recent computer and is only downloaded from that button, never by a click on Key points. Results are kept in this browser, so a reload shows them again until the text they came from changes. They belong to the person signed in: signing out, a session that ends or someone else signing in on the same browser removes them. The choices and results stay in this browser only. Where the browser does not have these models, or does not answer within a few seconds, the buttons stay hidden and nothing else changes.

## API for programs

Scripts, CI jobs and other servers use the same API as the page, with a personal token instead of a cookie. Make one in System > API tokens. It is shown once; SILO keeps only its SHA-256.

- A token acts as the person who made it and never has more rights than their role, checked again on every request. When the person is removed, their tokens go too. Tokens made while there are no accounts stop working when the first account is made.
- Scopes: `read` (everything you can GET), `run` (talk to residents, run workflows and tests, change residents, workflows and files), `approve` (tool requests, run approvals, proposed files, held changes) and `admin` (owner settings). A viewer can only give `read`, an operator `read`, `run` and `approve`.
- A token never signs in, changes a password, or manages accounts, tokens, single sign-on or the key vault.
- Tokens work from this computer only, unless made to work from anywhere (network and remote address). They expire after 7, 30, 90 or 365 days, or never. At most 300 requests a minute per token. Revoking one also closes its live streams. The audit log names the token behind each change.
- The API is described in OpenAPI 3.1 at `/api/openapi.json`, with the scope each call needs.
- Tests: `POST /api/workflows/{id}/evaluate` or `/api/agents/{id}/evaluate` starts them and returns the report; `GET /api/evals/{id}` follows it, `GET /api/evals/{id}/diff` compares it with the one before. `npm run eval` does all of that for CI.

```sh
curl -H "Authorization: Bearer $SILO_TOKEN" http://127.0.0.1:3000/api/state
```

```python
import os, requests
silo = requests.Session()
silo.headers["Authorization"] = "Bearer " + os.environ["SILO_TOKEN"]
base = "http://127.0.0.1:3000/api"
state = silo.get(base + "/state").json()
atlas = next(a for a in state["agents"] if a["name"] == "Atlas")
print(silo.post(f"{base}/agents/{atlas['id']}/chat", json={"message": "Summarize today's runs."}).json()["text"])
run = silo.post(f"{base}/workflows/{state['workflows'][0]['id']}/run", json={"input": "Weekly report"}).json()
```

### Python SDK

`sdk/python` is the `silo-os` package: only the standard library, Python 3.9 or newer, typed, with `Silo` and `AsyncSilo`. It waits and tries again after 429 as long as `Retry-After` says, raises `AuthError`, `PermissionDenied`, `NotFound`, `Conflict`, `RateLimited` and friends, and sends the token only over https or to this computer. `silo eval`, `silo ask` and `silo run` work from a terminal or CI. See [sdk/python/README.md](sdk/python/README.md); build it with `python -m build sdk/python`.

```python
from silo_os import Silo

assert not silo.evaluate("Weekly report")["worse"]
```

## Tables

In the Archive, Tables keep rows between runs: people seen, orders handled, leads, counts. They live in `data/tables.db`, apart from the state, at most 50 tables of 30 columns and 50,000 rows each.

- **Columns** have a name of letters, digits and _, and a kind: text, number, yes or no, date, JSON. A column can be needed (every row has a value) or unique (no two rows have the same value; text is compared without case, so Ana@x.ro and ana@x.ro are the same). A value that does not fit its column is refused with the reason, never guessed: `3,5` is a number, `da` and `nu` are yes and no, `15.11.2026` is a date read day first.
- **Changing columns.** A renamed column keeps its values, and the table steps of your workflows take the new name; a removed column is taken out of them too. A new kind of value, or a column made needed or unique, is checked against every row first: when a row does not fit, nothing changes and the rows are named. A table that a workflow uses cannot be deleted.
- **In the window**: search every column, sort by a column, add, change and delete rows, change the columns. Viewers only look.
- **CSV.** From a CSV file makes a table whose columns come from the first line, with the kind of value found from the rows (numbers, yes or no, dates; numbers with a leading 0, like phone numbers, stay text). Add from CSV puts rows into a table: all of them or none, and a value that does not fit says its line. Comma, semicolon or tab between values; up to 5 MB and 10,000 rows at once. The CSV download opens in Excel with its letters, and a cell that starts like a formula gets a quote mark first so it never runs.
- **Residents** with Use tables find, read and count rows without asking; the rows come marked as data. Adding, changing and deleting rows wait for your OK, and a change is not made twice when a run goes on after a stop.
- **Programs** use `/api/tables`: list and make tables, read rows with filters (`[{"column":"visits","op":"gt","value":3}]`, op eq, ne, contains, starts, gt, gte, lt, lte, empty, filled), add rows, change the row with a value (`matchOn`), change and delete rows, and send or get CSV. Reading needs the read scope, changes the run scope.
- A shared procedure names the table of a table step, and the SILO that reads it finds its own table with that name.

## Talk channels

In IT / Uplink, Talk channels, a resident answers people outside SILO: on your website, in Slack, on WhatsApp and in Microsoft Teams. Only an owner sets them up.

- **What the resident knows.** The resident gets the last six exchanges of a conversation, and none after two hours without a message. The conversations are kept in `data/talk.db`, so a restart does not start them over. The resident's chat in SILO is neither used nor changed. Pick a resident made for this: its instructions shape every answer, and anyone who can write may ask. Another resident, or turning a channel off, starts the resident's memory of its conversations over; the conversations stay in the inbox.
- **Inbox.** Talk channels > Inbox shows every conversation, newest first, with what was said, who answered and when. Search names and messages, or show only the ones waiting for your team, not read yet, with your team or with the resident, on one channel. Owners and operators read it and answer; viewers do not see it, because it holds what people outside wrote.
  - **Take over**: the resident stops answering that conversation. What the person writes waits in the inbox, and SILO tells your team, at most once every 5 minutes for each conversation. An answer the resident was still writing when you took over is kept as a note and not sent.
  - **Answer**: your answer goes back the way the person wrote: in the Slack thread, to the WhatsApp number, to the Teams conversation. The website chat picks it up on its own, every 5 seconds while your team has the conversation and every 15 while the chat is open, and shows a dot on its button when it is closed; an answer it has not shown yet also comes along with the visitor's next message. Answering takes the conversation over. It is sent only while the channel is on, and an answer that could not be sent is not kept as sent. WhatsApp takes a free answer only within 24 hours of the person's last message.
  - **Give back to the resident**: it answers again from there on, without the turns your team had. A conversation your team took over and left for a day goes back to the resident on its own, so nobody waits forever.
  - Taking over and giving back are noted in the conversation with who did it, and they, every answer and every delete go in the audit log. Delete removes a conversation for good. Conversations are kept 30 days after their last message (an owner sets 1 to 365 days in the inbox), at most 2000 conversations and the last 300 messages of each.
- **Tools.** On the website and WhatsApp the resident never uses tools, so nobody outside reaches your files, apps or residents through it. In Slack and Teams it uses its tools only if you allow it, and changes still wait for your OK in Signals.
- **Limits.** Each channel answers at most a number of messages a day (300 on the website and WhatsApp, 500 in Slack and Teams by default, 1 to 10000). One person may write 6 messages a minute (8 on the website, and 20 from one address). Messages are cut at 2000 characters (1000 on the website). Past a limit the person gets a short note, and so they do when SILO is paused or the model fails; the failure is in the log for you, at most once a minute.
- **Website chat.** A chat button on your own site, in a shadow root so it neither takes nor changes the page's styles. Give a title, a first message, a color and the sites it may be on; copy the script tag before `</body>`. Only pages of those sites can talk to it from a browser, and Try it opens SILO's own test page. Visitors on the internet need Open from anywhere. The visitor and the last 30 messages are kept in their browser only. New address on save retires the old snippet.
- **Slack.** Uses the bot token from Apps to answer, and the app's signing secret to check each event (older than 5 minutes is refused). It answers direct messages to the app and mentions of it, a mention in its thread. Slack sends an event again when it gets no OK within 3 seconds; SILO says OK at once and answers each event once. Messages of bots, its own too, edits and joins are left alone.
- **WhatsApp.** Meta's Cloud API: the phone number ID, a permanent access token and the app secret. SILO makes the verify token for the callback address. Each notification must carry Meta's signature, only messages to this number count, and a message that is not text gets a note that only text is read. The log names a person by their WhatsApp name, or by the last four digits.
- **Microsoft Teams.** An Azure Bot: its App ID, its client secret and, for a single tenant bot, the tenant. Each message must carry a Bot Framework token signed with one of its published keys, for this bot, in date, and naming the service address the answer goes to. Answers go only to Microsoft's own service addresses. The bot's own token is kept until shortly before it runs out.
- Slack, WhatsApp and Teams send messages to an internet address, so they need Open from anywhere; the addresses to give them appear in their windows.

## SILO for outside programs

An owner turns these on in System > Outside programs and picks the residents and workflows they may use. Nothing is exposed before that. Callers use an API token: its scopes and its person's role decide every call, residents still ask you before tools that need your OK, and the audit log names the token. Questions from outside start a new conversation and leave the resident's chat alone.

- **MCP server** at `/api/serve/mcp` (Streamable HTTP, JSON answers, protocol 2025-06-18, 2025-03-26 and 2024-11-05). Claude Desktop, Claude Code, Cursor, LangGraph, CrewAI and other MCP clients get `ask_<resident>` and `run_<workflow>` (scope run; a run waits up to 50 seconds, then gives its id), `silo_get_run` and `silo_pending` (read), `silo_decide` (approve), `silo_run_tests` (run) and `silo_test_report` (read). A token only sees the tools its scopes allow. System shows configs to copy; they never contain a token.
- **A2A agent** (Agent2Agent 0.3): the card is at `/.well-known/agent-card.json` (and `/agent.json`) while the agent is on, and it is public, as A2A cards are: it names what you exposed. JSON-RPC at `/api/serve/a2a`: `message/send` (blocking by default, up to two minutes), `message/stream` and `tasks/resubscribe` (server-sent events), `tasks/get` and `tasks/cancel`. Each skill is a resident or a workflow; a message without `metadata.skill` goes to the only one exposed or to the resident you pick. Text and data parts are accepted, not files. A follow-up with the same `contextId` lets a resident see the earlier turns. Tasks belong to the token that made them and stay in memory for a day (at most 300); push notifications are not supported.
- **Outside agents** (A2A client): add another agent by its address in System; SILO reads its card and keeps its token in the vault. The card must send tasks to its own origin, so it cannot redirect the token. Residents with `delegate` use `ask_agent`; the first task to each agent waits for your OK (allow always trusts that agent for that resident), and its answer is marked untrusted.

## Notebooks

Residents with `run_code` also get `notebook_run`: a persistent Python kernel per resident and notebook, like Jupyter but without needing Jupyter. Variables, imports and data stay between cells; the value of the last line is shown; matplotlib figures are kept as PNG. Each cell is approved like `run_code` (the exact code by its SHA-256, and where it runs: Docker without network when available, otherwise a local process on a copy of the workspace). A cell has 120 seconds (`SILO_NOTEBOOK_TIMEOUT` in ms); a cell over time stops the kernel. Files a cell writes become proposals. Notebooks are saved as `.ipynb` (nbformat 4.5) under `data/notebooks`; System shows them and can restart a kernel, save a copy to the Archive or delete them.

## Silo-to-Silo Radio

Residents can talk to residents of other SILO instances. Owners set it up in System > Silo-to-Silo Radio.

- Every silo makes its own Ed25519 key pair on its first start. The private half stays encrypted in the vault; the public key and its fingerprint are shown in System, and served at `/radio/identity` while the radio is on.
- To add another silo, write its address and press Read key. Before you save, ask its owner to read their fingerprint to you, by phone or in person, and compare. Then they add yours the same way. No secret is shared.
- Every transmission is signed with the sender's key and names the key it is for. Answers are signed by the receiver and carry the nonce of the question. The receiver knows the sender by the key that checks out, never by the name in the message.
- Addresses use https. Plain http works only on this computer and the local network (like `http://192.168.1.20:3000` or `http://silo.local:3000`); every question and answer is signed, so it cannot be forged on the way, but it is not encrypted. An address written without `http://` gets http on the local network and https elsewhere. The radio switch, this silo's name and its address are saved one at a time, as soon as you change them.
- Per silo: whether this silo sends to it, whether it takes transmissions from it, which residents it may reach (empty means all), messages an hour (default 30) and tokens a day (0 means no limit).
- Without a capability, a resident answers radio questions from what it knows, with no tools.
- The resident is found by exact name, then exact role. Nothing partial and no fallback. Requests older than five minutes and repeated nonces are refused, and inbound messages are marked untrusted.
- Residents with the `delegate` permission use the `radio_silo` tool, naming the silo when more than one is connected.
- An older SILO that only knows radio version 2 can still be added with a shared key (marked "old shared key"). Update both silos to use keys.

### Capabilities between silos

Under Give rights, an owner gives another silo the right to use some residents with some tools (`read_files`, `write_files`, `web`) in some folders, for some hours, with a budget of tokens and messages. For example: read only `reports/`, 2 hours, 50,000 tokens.

- The result is a signed token (`silocap1.…`) bound to the key of the silo it is for. No other silo can use it, and a change breaks the signature. Send it to the other owner, who adds it under Rights held.
- The silo that holds rights can pass on part of them (Pass on). Each link of the chain is signed by the silo that gives it and may only be narrower: fewer residents, tools and folders, a smaller budget, an earlier end. A third silo that the owner of the data has never met can then use exactly what it was passed, nothing more.
- Everything is checked where the data lives, with no central server: the chain starts with that silo's own key, each link narrows the one before, the last link names the key that signed the request, and no link is revoked or expired.
- The resident gets only those tools, file operations and folders, even if a local grant for it allows more.
- Budgets are counted at the silo that owns the data, for every link of the chain. A silo pays for what it passed on, too.
- Revoke stops a capability at once. A capability that was passed on is revoked at the silo that owns the data, which checks that the revocation is signed by the silo that signed that link. Revoking a link stops everything passed on from it.
- On the air lists what went over the radio: when, which silo, which resident, whether a capability was used, tokens, and why something was refused. It never keeps the messages.
- The map in System shows this silo in the middle and the others around it: the radio links (lit when used in the last ten minutes), the capabilities with a bar of the budget left, and the messages of the last minute and a half. On a phone it is a list.

## Guardrails

Set in System, under Guardrails (owners). They work on text, without a model, so they cost no tokens and add no wait.

- **Personal data sent to models.** With *Hidden as placeholders*, email addresses, phone numbers (with a country prefix, or the Romanian 07xx shape), IBANs and card numbers that pass their check digits, Romanian CNPs that pass theirs, and API keys go to the model as placeholders such as `[EMAIL_3fa9c1]`. So do the keys SILO itself holds and the words you list (client, project or people names). The answer comes back with the real values, as it streams too, and so do the tool calls the model makes: when a resident writes "send it to `[EMAIL_3fa9c1]`", the email goes to the real address. The conversation, the trace and the tools always keep the real values; only what leaves for the model is changed. The same value gets the same placeholder for as long as SILO runs, so a conversation sent again round after round stays the same to the model. A model on this computer (Ollama) gets the data as it is, unless you tick *Hide it from Ollama on this computer too*. Each model call that carried placeholders says what it hid in its trace, and the card counts them since SILO started. This covers every call to a chat model, test judges and the workflow builder included. Embeddings for meaning search and speech to text are not covered.
- **Orders inside tool results.** A web page, an email, an issue or a file can hold text written for the model rather than for a reader: "ignore your previous instructions", "you are now…", "send the API keys to…", "do not tell the user", fake system turns, invisible characters. The check knows these in English and Romanian. *Marked* (the default) puts a note before such a result telling the resident it is data, not instructions. *Ask* does the same, and from then on, for the rest of that answer, every tool that changes something (writes a file, acts in an app, runs code) waits for you in Requests, even for a resident you trust with that tool. *Block* also withholds the result itself. Each catch is in the card, in the activity log and in the audit log.
- **Rules**, one per line: where, what to do, and words or a `/pattern/`. Words are found as written, without case; a pattern between slashes is a regular expression. Lines starting with `#` are notes. At most 40.
  - `answer redact internal price list` hides those words in residents' answers as `[REDACTED]`.
  - `answer block /salary of \w+/` replaces a whole answer that matches.
  - `tool block delete_` stops any tool call whose name and arguments (read as `name {"json":"arguments"}`) match, also in test runs.
  - `tool ask /github.*close/` makes a matching call wait for you, every time.
  - A wrong line is refused with its number, and nothing of that save is kept.
  - Answer rules apply to the answer that is kept and sent (chat, workflow steps, talk channels, Telegram); what streams live to the page while the resident writes is not held back.
- **Try a text** shows, without a model, what a model would get, what would read as orders and what the answer rules would make of it (`POST /api/guardrails/check` with `{"text": "..."}`).

## Compliance report

In System, under Compliance report (owners), pick a period and choose Show, or download it as PDF, Markdown or JSON (`GET /api/compliance?from=YYYY-MM-DD&to=YYYY-MM-DD&format=pdf&download=1`; without `download` it answers JSON for a page or a program). It is built from the audit log, so it holds no message text, and it is meant as evidence for a GDPR record of processing or an EU AI Act review. It is not legal advice and does not certify anything.

- **Where data went.** Every model call is in the audit log as `model.call`: the resident, the provider and model, the host it was sent to, the tokens in and out, what the guardrails hid (as counts by kind) and where in SILO it came from. A call that failed after it was sent counts too. The report groups them by model and host, and says for each whether it runs on this computer, on your network or on the internet.
- **Residents.** For each: its model, its calls, how many went to the internet, its tool uses and failed tools, and which tools it uses without asking first.
- **Human oversight.** Tool requests allowed and denied, workflow approvals given and rejected, and what waits now. Decisions made on the page are in the audit log with the name of who made them, as are those from a phone or a Windows notification.
- **Guardrails.** How they are set and what they caught in the period.
- **Access and changes.** Sign-ins and failed ones, changes to settings, connections, accounts, tokens, connectors and Radio, changes that were refused, and capabilities given to other silos.
- **Set up now.** Accounts by role, single sign-on, API tokens, network access, where code runs, The Pact, how long the audit log is kept and whether its chain has its own key, where the data is kept, talk channels open to people outside, and capabilities given to other silos.
- **Findings** come first, worst first: a broken audit chain, model calls to the internet with hiding off, no accounts, residents that act without asking, an audit log without its own key or kept for less than six months, many failed sign-ins, decisions that wait, and talk channels where people outside should be told they are talking to an AI.
- Each file made is itself in the audit log (`compliance.report`). Model calls are in the audit log from this version on, so an earlier period shows none.

## Data and limits

- `data/state.db` (SQLite) holds residents, conversations, workflows, runs, traces and the activity log. Each save writes only what changed, in one transaction, so a crash leaves the last complete save. Every row has a checksum, and a damaged database is moved aside and rebuilt from the copies below.
- A save does not serialize what cannot have changed. Finished runs, jobs and traces and the activity log are compared once more after they finish, and once they have stayed the same for ten seconds they are skipped. A change to one of them names it at the place it is made (`persist(row)`, or `store.touch(row)` where no save follows at once, as for a span that ends after its trace), so it is written at once. Every row is still compared once a minute, also when nothing else saves (the store's own timer runs it), and when the server stops. A change that only this comparison finds is still saved, but counted and shown in System under Updates and start, with the row, so the place that forgot to name it can be fixed; `SILO_STRICT_SAVES=<file>` writes each one to a file, which the tests use. On a silo with 120 long runs and 300 traces this takes a save from about 18 ms to about 1 ms and from 11 MB of JSON to under 100 KB.
- System, under Updates and start, shows what saves cost (the last, the average and the slowest, and how many rows were serialized or skipped), how late the server answers (typical, 1 in 100 and slowest, over the last five to ten minutes; on Windows about 15 ms is the system timer itself) and how the live pages keep up.
- `data/state.json` is a readable copy, written every five minutes when something changed and when the server stops. `data/state.json.bak` is the copy before it, and SQLite also keeps three hourly snapshots. To go back to a copy, stop the server and put it in place as `data/state.json`: on the next start a `state.json` changed by hand is loaded instead of the database.
- `workspace/` holds the shared files. They stay on this computer unless a resident with read access sends them to an external provider.
- Text files residents can read: txt, md, json, csv, js, ts, html, css, yaml, yml, up to 30 KB per file. Documents (pdf, docx, xlsx, xlsm, pptx, odt, ods, odp) up to 15 MB, of which the first 40,000 characters of text are read. Files you add in the Archive can be up to 25 MB. The file list shows at most 150 files. Web pages are cut at 20,000 characters. The last 20 messages are sent as chat context, and the last 100 are kept per resident.
- `data/secrets.enc` and `data/vault.key` hold your keys, tokens and passwords for connectors and channels, encrypted.
- Only relative file paths are accepted. Paths that leave the folder, alternate data streams, reserved Windows names and symbolic links are refused. The server checks the Host header, needs a session cookie, and needs the same Origin plus a CSRF token for every change. If the server restarts, the page gets a new session on its own.
- Exports contain your conversations and history. Treat them as private.
- The page asks for the state every two seconds, but the server only sends it again when something changed. Otherwise the answer is empty.
- The registry shows 48 residents at a time. Show more loads the next 48, and searching or picking a sector starts over.

## People and network access

With no accounts SILO answers only on this computer and asks nobody to sign in. In System, create an owner account to turn on sign-in. Owners can add more people as:

- **Owner**: everything, including keys, connectors, channels, spending, settings and people.
- **Operator**: talks to residents, runs and edits workflows, approves requests. Cannot change keys, connectors, channels, spending, settings or people. Runs app steps but cannot add, change or move one, nor bring one back from an older version, because an app step uses your accounts and connectors directly; the editor shows them locked. Removing one is allowed.
- **Viewer**: looks at everything and changes nothing.

Sign-in happens on a green terminal floating in the shaft of the silo. Behind it, in phosphor green, the camera falls down the shaft past eight-sided floors with lit windows, pipes, a spiral stair and bridges, then slows to a drift while the view turns and steam moves. The terminal comes out of the dark and leans toward the pointer, the title resolves out of random signs, and the Warden wakes and asks for your name and password. Any key or click finishes the opening at once and lands in the next field. A wrong password turns the shaft amber and sounds the alarm; the right one sends the camera diving down the shaft into the silo. With reduced motion turned on in your system, it all shows at once without animation.

Passwords are hashed with scrypt. Ten wrong passwords from one address lock it out for ten minutes. An owner can open SILO to other devices on the network. It takes effect after a restart, and the server prints the addresses to use. Traffic is plain HTTP, so only do this on a network you trust, or put a TLS proxy in front. If you lose every owner password, stop the server and remove the `users` list from `data/state.json`.

### Open from anywhere

System, Open from anywhere, gives SILO a secure HTTPS address through a Cloudflare Tunnel, for your phone or any other network. SILO keeps listening only on this computer; cloudflared makes an outgoing connection to Cloudflare and brings the requests back. Nothing is opened on your router and no firewall rule is needed.

- It needs an owner account, and everyone signs in. Over the tunnel the session cookie is HTTPS only, the browser is told to stay on HTTPS, and the page only accepts requests from the tunnel address.
- Ten wrong passwords from one internet address lock that address for ten minutes, and thirty wrong passwords from the whole internet lock all sign-ins over the tunnel for ten minutes. Signing in on this computer keeps working.
- One-time links from Windows notifications only work on this computer.
- **Quick address**: free and without an account, a random `https://....trycloudflare.com` address that changes each time SILO starts. When the phone bot is connected, it sends you the new address.
- **Your own domain**: create a tunnel in the Cloudflare dashboard (Networks, Tunnels), paste its token, and add a public hostname with service `http://127.0.0.1:3000`. The address stays the same. The token is kept in the encrypted vault and given to cloudflared through its environment, not its command line.
- cloudflared is found in `data/bin`, Program Files, WinGet or PATH. The Download button gets it from Cloudflare's GitHub releases and keeps it only if it carries a valid signature from Cloudflare. You can also run `winget install --id Cloudflare.cloudflared`.

### Single sign-on

In System, Single sign-on, people sign in with your company account through OpenID Connect: Microsoft Entra ID, Google Workspace, Okta, Auth0, Keycloak or any provider with discovery. Register SILO in your provider as a web app, with the redirect address the card shows (`http://127.0.0.1:3000/sso/callback`, or your tunnel address), then give SILO the issuer, the client ID and the secret. It needs an owner account first.

- SILO uses the authorization code flow with PKCE, a nonce, and a state tied to the browser that started the sign-in. It checks the id_token itself: the signature against the provider's published keys, the issuer, the audience, the time and the nonce.
- The account is made at the first sign-in. You choose which email domains get in, and what role new people get: none, viewer or operator.
- Group rules give roles from a claim (`groups`, `roles`, or a path like `realm_access.roles`). With rules, the role follows the provider at every sign-in, and the last owner always stays owner.
- An owner who removes someone keeps them out, until the owner lets removed people in again.
- Names and passwords can stay on everywhere, or only work on the SILO computer as a way back in.

### Audit log

Every sign-in (also the failed ones), every change made through SILO, every decision from the page, a phone or a Windows notification, every webhook start and every tool a resident uses goes into `data/audit`, one file per month. Each record says who, when, from which address and how it went. Passwords, keys and message text are never written into it.

Each record holds an HMAC of the one before it, made with a key from the encrypted vault. Check the chain in System, Audit log: a record that is changed, removed or slipped in shows up, with the file and line. Export a date range as CSV (for Excel) or JSON lines (for a SIEM). You choose how long records are kept: always, or 1 to 7 years.

### OpenTelemetry

In System, OpenTelemetry, SILO sends traces to your own collector over OTLP/HTTP with JSON: the OpenTelemetry Collector, Grafana, Honeycomb, Datadog, Jaeger, Langfuse and others. Every conversation, workflow run and goal is a trace; model calls, tool uses, questions to other residents and approvals are spans, with the GenAI conventions (`gen_ai.request.model`, `gen_ai.usage.input_tokens` and so on) plus cost. The audit log can go along as logs. Prompts and answers are never sent; tool arguments only when you turn that on, and without secrets. Headers, such as an API key for the collector, are kept in the vault. Plain http is only allowed to this computer or your own network. When the collector is away, SILO keeps up to 5,000 spans and tries again, waiting up to five minutes.

### Speed on slow connections

Answers are compressed with Brotli or gzip. Files are checked with an ETag, so a reload sends only what changed, and the 3D library is cached for a week. SILO can be added to the home screen of a phone as an app.

### Speed in the page

- A live channel (server-sent events, compressed, with everything of one tick sent and flushed at once) sends the silo state once, then only what changed: one resident that starts working is a patch of a few hundred bytes instead of the whole state, and it arrives within about 150 ms instead of on the next two second check. The text a resident is writing comes the same way, a few letters at a time. When the channel is down, the page goes back to checking every two seconds.
- A page on a slow connection never makes the server pile up updates for it. While it has not taken what it was sent (more than 256 KB waiting), it is skipped; when it catches up it gets one patch for everything it missed, or the whole state when that is smaller. A page that stays behind for a minute, or with more than 4 MB waiting, is closed and connects again by itself.
- Pages get a lighter state than the API. A finished run comes as its summary and its steps without their output, journal or checkpoints; the whole run is fetched when it is opened, copied or run again, and kept until it changes. Runs still going come the same light way: the steps without their output, input and output cut to 300 characters, and the plan as the kind and resident of each step. The page fetches the whole run when it is opened and keeps the live status from the light one. Measured with `npm run bench:live -- --active 10` (ten unfinished heavy runs with plans, snapshots, journals and checkpoints, through the same slow connection): a page took about 2.55 s for 617 KB before, and takes about 0.43 s for 93 KB now. `/api/state` gives the whole state as before; pages ask for `/api/state?view=page`. The whole state message is made once and shared by every page instead of being read and written again for each. Measured with `npm run bench:live` (150 finished runs, four pages through a connection of 512 KB/s with 150 ms delay): a page that connects again took about 9.4 s for 2.3 MB before, and takes about 0.4 s for 91 KB now.
- Every script is asked for at once (module preload), so the page is ready in well under 100 ms on this computer instead of over a second.
- The artwork loads as WebP (about 0.7 MB instead of 3.5 MB), with the PNG as a fallback.
- The shaders compile in the background where the graphics driver allows it, and the 432 residents are painted by workers off the main thread (OffscreenCanvas), so the world appears without a half second stall.
- The 3D picture adapts its sharpness to the device in both directions: it starts sharp, steps down when frames take too long and back up when there is room, up to the screen's own resolution (1.5 on phones).
- Shadows are drawn again only when they would come out different: when the camera changes level, levels come into view or the machines at the bottom turn. Elsewhere the last shadow map is reused, which saves about a sixth of the draw calls in each frame with exactly the same picture.
- Moving between terminals cross-fades (View Transitions) and dialogs fade out, unless the system asks for reduced motion. Settings cards further down the page are only laid out when they scroll into view.

## Limits

One SILO is one process with its data in SQLite on one machine. It does not spread one silo over several servers: for more work at once, give it a bigger machine, or let the durable job queue run more jobs at a time (`queue.maxConcurrent` through `POST /api/settings`, 4 by default, at most 32); for separate teams or environments, run more SILOs, link them with Radio, and move workflows between them through Git.

SILO runs on your own computer, or in a container on your own server. It is not a hosted service: it runs while you are signed in, starts with you when start at sign-in is on, and runs before anyone signs in when it starts with the computer. It does not make voice or video calls. The phone bot and email triggers only work while the server runs. Local code runs are not a full sandbox, so keep approval on, or install Docker. Scheduling stops when the server stops. When it starts again, a workflow whose time passed runs once or is skipped, as its missed-time choice says, however many times were missed.
